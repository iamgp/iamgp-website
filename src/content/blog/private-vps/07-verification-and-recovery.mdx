# Checking access, restarts and recovery

*Part 7 of 7. [Previous: Amp deployments](06-amp-runner-and-deployments.mdx) · [Series index](README.mdx)*

The setup is useful when I can leave work running, return from another device and recover access if the private connection fails. This final post checks those outcomes after all the components are installed. Run the checks through fresh connections, as an existing terminal can keep working after a configuration change that prevents the next login.

## Check everyday access and deployments

On the Mac, open `ssh workbench` and `ssh workbench-admin`. Confirm the account in each session. `operator` should authenticate with `sudo -v`; `builder` should have only the preview-helper permission:

~~~sh
whoami
hostname
sudo -n -l
~~~

As `builder`, an unrelated privileged command should fail:

~~~sh
sudo -n /usr/bin/id
~~~

Open the VPS workspace in Rex on the Mac and iPhone. Run `whoami` and `hostname` in each terminal to confirm that both reach `builder` on the VPS, then open the preview on both devices. On the Mac, a terminal request checks HTTPS without relying on a cached browser page:

~~~sh
curl --fail --show-error https://workbench.YOUR_TAILNET.ts.net:8443/
~~~

From outside Tailscale, confirm that the VPS's public address does not expose SSH, Rex or the preview ports. Run the Tailscale policy tests too, including the phone's blocked SSH and database connections.

In the project's directory, inspect `docker compose ps` and its logs. Check the host listener with `ss -lnt` and the preview mapping with `sudo -n /usr/local/sbin/workbench-preview status`. The application should respond locally before you troubleshoot HTTPS. If it does, follow the request through the Serve mapping and then the client-side Tailscale connection.

For a running container, compare its actual resource limits with the Compose configuration:

~~~sh
docker exec CONTAINER_NAME cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max /sys/fs/cgroup/pids.max
~~~

Replace `CONTAINER_NAME` with the container you are checking. For a job that writes project files, check the output's owner on the host as in part 3.

## Test restart and recovery

First close the client connection while a detached application is running. Reconnect and check that the application still responds. This tests whether it depends on the terminal staying open.

Then reboot the VPS through the administrator account. A reboot ends running terminals and jobs; enabled services and container restart policies determine what returns. After reconnecting, run these checks as `builder`:

~~~sh
systemctl --user is-active docker rex amp-workbench
systemctl --user is-enabled docker rex amp-workbench
docker context show
docker compose -f /home/builder/projects/demo/compose.yaml ps
amp runner list
~~~

Reopen Rex and the private preview from both devices. Check that Amp can start a new task on the runner. If a service has not returned, read its journal with `journalctl --user -u SERVICE_NAME -n 50 --no-pager`, replacing `SERVICE_NAME` with the relevant unit.

Finally, open the provider's authenticated browser console and log in locally as root using the recovery credential in 1Password. Confirm the hostname, then log out. This route needs to work even when private networking is unavailable. Test it after disabling root SSH, as the console and SSH use different login paths. Console access restores control of the machine; recovering lost application data is a separate task.

Keep a private note of the SSH aliases, Rex address, project ports and service names, plus a reference to the recovery credential. Update it when those details change. That is enough to find the right account and service when something stops working.

For maintenance, keep Ubuntu's security updates enabled, update Rex alongside its clients and keep a known working application version before redeploying. The machine is ready for everyday development when the client, reboot and recovery checks all work together.
