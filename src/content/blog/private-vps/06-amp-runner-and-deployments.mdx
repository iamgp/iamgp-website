# Deploying to the VPS with an Amp runner

[Amp](https://ampcode.com/docs) is an AI coding tool that can edit files and run terminal commands. Its runner lets me send that work to the VPS from the app, using the account setup and private previews from the previous posts. The runner is a process on the server, so work can continue when the Mac is closed.

The deployment pattern also applies to other coding agents that can execute on a Linux host. The development account, rootless Docker and preview helper can stay the same; the remote-execution setup and instruction files depend on the tool. I use Amp here, so the following steps cover its runner and global settings.

## Run Amp as a persistent service

From the Mac, open `ssh workbench` as `builder`. On the VPS, download and inspect the installer from Amp's [CLI instructions](https://ampcode.com/docs/cli), then run it without sudo:

~~~sh
install -d -m 700 "$HOME/.cache/workbench"
curl -fsSLo "$HOME/.cache/workbench/amp-install.sh" https://ampcode.com/install.sh
less "$HOME/.cache/workbench/amp-install.sh"
bash "$HOME/.cache/workbench/amp-install.sh"
~~~

Press `q` to leave `less`. After installation, run `exit` and reconnect from the Mac with `ssh workbench` so the new shell picks up any PATH change. PATH is the list of directories searched for commands. Then check the binary and sign in on the VPS:

~~~sh
command -v amp
amp --version
amp login
amp account list
~~~

For the default installation used below, `command -v amp` should return `/home/builder/.local/bin/amp`, and `amp --version` should print the installed version. If the path differs, use that absolute path for both executable lines in the service unit. Open the login link in the Mac's browser and approve the account you want to control this runner. Signing in to the Mac app does not sign in a separate Linux installation, so note the account's user ID for the service below. Keep the VPS configuration separate from any unrelated Mac integrations. The runner has access to `builder`'s files and Docker daemon, so use it for trusted development work. Selecting a served project directory is not a sandbox around that directory.

Git records a project's source history in a repository, and Amp's discovery option looks for these repositories. The existing demo lives beneath `/home/builder/projects`. Still as `builder` on the VPS, initialise it only if it is not already a repository:

~~~sh
git -C "$HOME/projects/demo" init -b main
~~~

In this `builder` session, run `mkdir -p ~/.config/systemd/user`, then open `nano ~/.config/systemd/user/amp-workbench.service` and save the following. Replace `YOUR_AMP_USER_ID` and check that Amp is installed at `%h/.local/bin/amp`, where `%h` means the user's home directory. Adjust both executable paths if your installation differs.

~~~ini
[Unit]
Description=Private Amp development runner
After=docker.service
Wants=docker.service

[Service]
Type=simple
WorkingDirectory=%h/projects
Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin
UnsetEnvironment=AMP_API_KEY AMP_URL
ExecStartPre=%h/.local/bin/amp account switch YOUR_AMP_USER_ID
ExecStart=%h/.local/bin/amp --no-tui --runner-id workbench --remote-control-terminal --discover-dirs
Restart=always
RestartSec=5
UMask=0077
MemoryMax=4G
CPUQuota=150%
TasksMax=1024
Nice=5
TimeoutStopSec=45

[Install]
WantedBy=default.target
~~~

The pre-start command selects the intended account on every start. A saved account appearing in `amp account list` does not prove that a new process will use it. Clearing the two environment overrides prevents them from selecting a different credential or server. Amp's [account documentation](https://ampcode.com/docs/cli#manage-cli-accounts) explains the precedence.

`--no-tui` runs the service without an interactive terminal interface. `--runner-id` gives the runner a stable name. `--discover-dirs` finds Git checkouts beneath its working directory, and `--remote-control-terminal` enables remote terminal access. These options are documented in [Amp's runner guide](https://ampcode.com/docs/cli/runners).

Start the service:

~~~sh
systemctl --user daemon-reload
systemctl --user enable --now amp-workbench
journalctl --user -u amp-workbench -n 30 --no-pager
amp runner list
amp runner dirs list
~~~

Check that the runner appears under the intended account and includes the demo project. The checks should identify the following, shown schematically because table formatting varies by version:

~~~text
amp runner list:
  workbench ... <YOUR_AMP_USER_ID> ... online

amp runner dirs list:
  /home/builder/projects/demo
~~~

You can also run `systemctl --user is-active amp-workbench`, which should print `active`. Lingering, enabled in part 3, lets the service start without an interactive login.

The service budgets above cover Amp's processes. Keep the separate Compose limits for application containers and the overall development-account limit from part 3.

## Make the deployment instructions available

On the Mac, save the example [DEPLOYMENT.md](/examples/private-vps/DEPLOYMENT.md) in `~/Downloads/private-vps-examples`. It describes how to choose unused ports, build a rootless Compose application and check local health before publishing a preview. It also requires a source revision and a previous working version for rollback.

In a local Mac terminal, run `cd ~/Downloads/private-vps-examples` and `nano DEPLOYMENT.md` to adapt it to your projects. Then install it on the VPS:

~~~sh
ssh workbench 'install -d -m 700 /home/builder/.config/workbench'
scp DEPLOYMENT.md workbench:/home/builder/.config/workbench/DEPLOYMENT.md
ssh workbench 'chmod 600 /home/builder/.config/workbench/DEPLOYMENT.md'
~~~

From the Mac, open `ssh workbench` again. On the VPS, run `mkdir -p ~/.config/amp`, then open `nano ~/.config/amp/AGENTS.md` and append this pointer alongside any existing guidance:

~~~markdown
For VPS deployments, private previews and application restarts, read /home/builder/.config/workbench/DEPLOYMENT.md before making changes.
~~~

Back in the Amp app or website on the Mac, open personal Settings, then Instructions, and edit Global AGENTS.md. Append the following so requests made from the Mac can find the runner too:

~~~markdown
## Private VPS deployments

When I ask to deploy development work to my VPS, use runner workbench and a named project under /home/builder/projects.

If already running on that VPS, read /home/builder/.config/workbench/DEPLOYMENT.md and deploy there. Otherwise start a thread on runner workbench in the project's directory. Pass the repository and revision, or the available source, with the requested behaviour.

Follow the server's deployment procedure. Return the private HTTPS URL and report which health and client checks passed. Use project-specific credentials. Keep public sharing, production releases and privileged administration subject to their existing approval rules.
~~~

The local pointer applies on the VPS. The global guidance helps route a request there, without asking a thread already on the server to start another copy of itself. [Amp's AGENTS.md documentation](https://ampcode.com/docs/customize/agents-md) describes where these instructions apply. They guide behaviour; the Linux accounts and preview helper enforce permissions.

## Deploy a project

In Amp, choose `workbench` and the demo project. Ask it to deploy the project using the server procedure and return the private URL. For the optional CLI route, use a local Mac terminal, not the VPS shell. Install the Amp CLI on the Mac as well and run `amp login` with the same account. You can then make the request through [execute mode](https://ampcode.com/docs/cli/execute-mode):

~~~sh
amp --executor runner:workbench --runner-dir /home/builder/projects/demo -x 'Deploy this project privately using the server runbook. Verify local health and return the private HTTPS URL. Preserve other projects.'
~~~

Check the completed thread, as a thread link can arrive before the work has finished. Then open the returned URL from the Mac or phone with Tailscale connected and check the application's behaviour.

For a private repository, the runner also needs the intended revision and a repository-scoped credential or a source transfer. A registered runner alone does not establish repository access. The useful result is the requested version running at a private URL, with a way to return to the previous version if it fails.
