# Deploying to the VPS with an Amp runner

*Part 6 of 7. [Previous: project secrets](05-secrets-with-1password.mdx) · [Series index](README.mdx) · [Next: checks and recovery](07-verification-and-recovery.mdx)*

An Amp runner lets me send development work to the VPS from the app. The files and commands stay on the server, so the Mac does not need to remain open while the work runs. I also want Amp to deploy there when asked. That needs a persistent runner and instructions describing the deployment path already built in this series.

## Run Amp as a persistent service

Connect as `builder` and install Amp using its [CLI instructions](https://ampcode.com/docs/cli). Then check the binary and sign in:

~~~sh
command -v amp
amp --version
amp login
amp account list
~~~

Use the account you want to control this runner. Signing in to the Mac app does not sign in a separate Linux installation, so note the account's user ID for the service below. Keep the VPS configuration separate from any unrelated Mac integrations. The runner has access to `builder`'s files and Docker daemon, so use it for trusted development work. Selecting a served project directory is not a sandbox around that directory.

Projects live beneath `/home/builder/projects`. To make the existing demo directory discoverable as a Git project, initialise it if it is not already a repository:

~~~sh
git -C "$HOME/projects/demo" init -b main
~~~

Save the following as `~/.config/systemd/user/amp-workbench.service`. Replace `YOUR_AMP_USER_ID` and check that Amp is installed at `%h/.local/bin/amp`, where `%h` means the user's home directory. Adjust both executable paths if your installation differs.

~~~ini
[Unit]
Description=Private Amp development runner
After=docker.service
Wants=docker.service

[Service]
Type=simple
WorkingDirectory=%h/projects
Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin
UnsetEnvironment=AMP_API_KEY AMP_URL
ExecStartPre=%h/.local/bin/amp account switch YOUR_AMP_USER_ID
ExecStart=%h/.local/bin/amp --no-tui --runner-id workbench --remote-control-terminal --discover-dirs
Restart=always
RestartSec=5
UMask=0077
MemoryMax=4G
CPUQuota=150%
TasksMax=1024
Nice=5
TimeoutStopSec=45

[Install]
WantedBy=default.target
~~~

The pre-start command selects the intended account on every start. A saved account appearing in `amp account list` does not prove that a new process will use it. Clearing the two environment overrides prevents them from selecting a different credential or server. Amp's [account documentation](https://ampcode.com/docs/cli#manage-cli-accounts) explains the precedence.

`--runner-id` gives the runner a stable name. `--discover-dirs` finds Git checkouts beneath its working directory, and `--remote-control-terminal` enables remote terminal access. These options are documented in [Amp's runner guide](https://ampcode.com/docs/cli/runners).

Start the service:

~~~sh
systemctl --user daemon-reload
systemctl --user enable --now amp-workbench
journalctl --user -u amp-workbench -n 30 --no-pager
amp runner list
amp runner dirs list
~~~

Check that the runner appears under the intended account and includes the demo project. Lingering, enabled in part 3, lets the service start without an interactive login.

The service budgets above cover Amp's processes. Keep the separate Compose limits for application containers and the overall development-account limit from part 3.

## Make the deployment instructions available

Download the example [DEPLOYMENT.md](/examples/private-vps/DEPLOYMENT.md). It describes how to choose unused ports, build a rootless Compose application and check local health before publishing a preview. It also requires a source revision and a previous working version for rollback.

Adapt it to your projects, then install it from the Mac:

~~~sh
ssh workbench 'install -d -m 700 /home/builder/.config/workbench'
scp DEPLOYMENT.md workbench:/home/builder/.config/workbench/DEPLOYMENT.md
ssh workbench 'chmod 600 /home/builder/.config/workbench/DEPLOYMENT.md'
~~~

In `~/.config/amp/AGENTS.md` on the VPS, add this pointer alongside any existing guidance:

~~~markdown
For VPS deployments, private previews and application restarts, read /home/builder/.config/workbench/DEPLOYMENT.md before making changes.
~~~

In Amp's personal settings, open Instructions and edit Global AGENTS.md. Append the following so requests made from the Mac can find the runner too:

~~~markdown
## Private VPS deployments

When I ask to deploy development work to my VPS, use runner workbench and a named project under /home/builder/projects.

If already running on that VPS, read /home/builder/.config/workbench/DEPLOYMENT.md and deploy there. Otherwise start a thread on runner workbench in the project's directory. Pass the repository and revision, or the available source, with the requested behaviour.

Follow the server's deployment procedure. Return the private HTTPS URL and report which health and client checks passed. Use project-specific credentials. Keep public sharing, production releases and privileged administration subject to their existing approval rules.
~~~

The local pointer applies on the VPS. The global guidance helps route a request there, without asking a thread already on the server to start another copy of itself. [Amp's AGENTS.md documentation](https://ampcode.com/docs/customize/agents-md) describes where these instructions apply. They guide behaviour; the Linux accounts and preview helper enforce permissions.

## Deploy a project

In Amp, choose `workbench` and the demo project. Ask it to deploy the project using the server procedure and return the private URL. With an authenticated Mac CLI, you can make the same request through [execute mode](https://ampcode.com/docs/cli/execute-mode):

~~~sh
amp --executor runner:workbench --runner-dir /home/builder/projects/demo -x 'Deploy this project privately using the server runbook. Verify local health and return the private HTTPS URL. Preserve other projects.'
~~~

Check the completed thread, as a thread link can arrive before the work has finished. Then open the returned URL from the Mac or phone with Tailscale connected and check the application's behaviour.

For a private repository, the runner also needs the intended revision and a repository-scoped credential or a source transfer. A registered runner alone does not establish repository access. The useful result is the requested version running at a private URL, with a way to return to the previous version if it fails.
