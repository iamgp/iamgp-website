# Private SSH access with Tailscale and 1Password

*Part 2 of 7. [Previous: the setup](01-architecture.mdx) · [Series index](README.mdx) · [Next: rootless Docker](03-rootless-docker.mdx)*

I use ordinary SSH over Tailscale, with the private key held in 1Password on my Mac. Tailscale controls which devices can reach SSH; the SSH key controls which Linux account I can log into. Start in your VPS provider's authenticated browser console as root and keep it open until private access works. This route is also how you will recover access after disabling public SSH.

## Create the accounts and private connection

Save the root recovery credential in 1Password, alongside a note explaining how to open the provider console. Keep the administrator's sudo password in a separately labelled field. In the console, create the accounts used throughout the series:

~~~sh
adduser operator
usermod -aG sudo operator
adduser --disabled-password --gecos '' builder
~~~

Set `operator`'s password when prompted. `builder` will use an SSH key and does not need a password or membership of the `sudo` group. Create or select a key in 1Password and copy its public key into `/home/operator/.ssh/authorized_keys` and `/home/builder/.ssh/authorized_keys`. Each `.ssh` directory should have mode `0700`, its `authorized_keys` file mode `0600`, and both should belong to the relevant user. Keep the private key in 1Password.

Install Tailscale in the provider console. To inspect its official installer before running it:

~~~sh
curl -fsSLo /root/tailscale-install.sh https://tailscale.com/install.sh
less /root/tailscale-install.sh
sh /root/tailscale-install.sh
~~~

The [complete example policy](/examples/private-vps/tailscale-policy.json) contains the grants and their tests. Replace its uppercase placeholders using the device addresses and user identity shown in your Tailscale admin console. It allows these connections:

| Client | Destination | Access |
| --- | --- | --- |
| Mac | `workbench` | SSH on port 22 |
| Mac and iPhone | `workbench-rex` | Rex on port 443 |
| Your signed-in personal devices | `workbench` | Private previews on ports 8443 to 8499 |

It also defines the server tags and tests that the phone cannot reach SSH or a database port. If the Mac Rex client uses its own embedded Tailscale device, include that address in the Rex grant too.

Adapt this policy to your existing network. Tailscale permissions are additive, so an existing broad allow rule can defeat the restrictions above. Review those rules and get the policy tests passing before proceeding. [Tailscale's grants reference](https://tailscale.com/docs/reference/syntax/grants) explains the syntax.

Then enrol the VPS from the provider console:

~~~sh
hostnamectl set-hostname workbench
tailscale up --hostname=workbench --advertise-tags=tag:workbench
tailscale status
~~~

Complete the displayed sign-in and check the device name and tag. Enable MagicDNS so that `workbench.YOUR_TAILNET.ts.net` resolves on your clients. This setup uses OpenSSH, so you do not need to enable Tailscale SSH.

## Connect SSH through 1Password

In the provider console, display the host-key fingerprint:

~~~sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
~~~

On the Mac, collect the key offered through Tailscale and display its fingerprint:

~~~sh
ssh-keyscan -t ed25519 workbench.YOUR_TAILNET.ts.net > workbench-host-key
ssh-keygen -lf workbench-host-key
~~~

Compare the fingerprints. [`ssh-keyscan` collects a key without proving who owns it](https://man.openbsd.org/ssh-keyscan); the provider console gives you an independent value to compare. If they match, add the key on the Mac:

~~~sh
mkdir -p ~/.ssh
chmod 700 ~/.ssh
cat workbench-host-key >> ~/.ssh/known_hosts
chmod 600 ~/.ssh/known_hosts
~~~

Enable 1Password's SSH agent on the Mac so SSH can use the vault's key without exporting the private key. Download the selected public key to `~/.ssh/workbench.pub`, then add these entries to `~/.ssh/config`:

~~~sshconfig
Host workbench
    HostName workbench.YOUR_TAILNET.ts.net
    User builder
    IdentityAgent ~/.1password/agent.sock
    IdentityFile ~/.ssh/workbench.pub
    IdentitiesOnly yes
    StrictHostKeyChecking yes
    ForwardAgent no
    ServerAliveInterval 30

Host workbench-admin
    HostName workbench.YOUR_TAILNET.ts.net
    User operator
    IdentityAgent ~/.1password/agent.sock
    IdentityFile ~/.ssh/workbench.pub
    IdentitiesOnly yes
    StrictHostKeyChecking yes
    ForwardAgent no
    ServerAliveInterval 30
~~~

Use the agent socket path configured by your 1Password installation. `IdentityFile` points to the public key so SSH asks the agent for the matching private key. `IdentitiesOnly` avoids offering every other key in the vault. This follows [1Password's host-specific configuration](https://www.1password.dev/ssh/agent/advanced).

Open fresh connections with `ssh workbench` and `ssh workbench-admin`. Check `whoami` in each. As `operator`, run `sudo -v` and authenticate with its password. If key selection is wrong, `ssh -G workbench` shows the effective client configuration.

## Close public access

Once both private logins work, create `/etc/ssh/sshd_config.d/00-workbench.conf` as administrator:

~~~text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowUsers operator builder
AllowAgentForwarding no
X11Forwarding no
MaxAuthTries 3
~~~

Run `sudo sshd -t` before reloading SSH with `sudo systemctl reload ssh`. Check `sudo sshd -T` too, as cloud-image configuration can affect the final settings. Keep the existing console and administrator session open while testing another fresh login.

Use Ubuntu's [UFW firewall](https://documentation.ubuntu.com/security/security-features/network/firewall/) to allow SSH and the preview range through the Tailscale interface, along with Tailscale's UDP transport port:

~~~sh
sudo apt install ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow in on tailscale0 proto tcp to any port 22
sudo ufw allow in on tailscale0 proto tcp to any port 8443:8499
sudo ufw allow 41641/udp
sudo ufw enable
sudo ufw status verbose
~~~

Remove any existing public SSH allow rule before relying on this configuration. Tailscale's policy remains necessary, including for Rex's embedded network connection.

Finish by testing a new private administrator login and a root login through the provider console. Disabling root SSH does not disable the provider's local console login. You now have separate routes for everyday work, administration and recovery.
