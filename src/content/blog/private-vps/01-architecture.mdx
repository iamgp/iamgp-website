# Deciding what each tool is responsible for

*Part 1 of 7. [Series index](README.mdx) · [Next: private access](02-private-access-and-ssh.mdx)*

I wanted a development VPS that I could use from my Mac and phone. It needed to keep applications running when I closed the laptop, give me private browser previews, and let Amp deploy work without turning every project into a new infrastructure exercise.

The tools were already familiar: a VPS, Tailscale, 1Password, Rex and Cloudflare. The useful work was deciding how they should fit together.

This series starts with a fresh Ubuntu 24.04 LTS machine. I wanted a setup I could maintain and troubleshoot, with a clear record of how each part works.

## Start with the work

The main use is development. I want to open a terminal, work in a project, ask an agent to make changes, deploy a preview and inspect it from another device. I do not need strangers to reach that preview.

That gives the machine a fairly narrow job. It runs the development tools and applications. My Mac and iPhone are clients. The laptop can have its own local projects and its own Rex server, but the VPS workspace should not depend on either of those being available.

I also want a clear answer to a less pleasant question: what can an agent reach if I run it here? That answer changes depending on whether the agent runs in a constrained container or directly as the development account.

## Give each component one clear role

| Component | Its job |
| --- | --- |
| VPS | Run project files, containers, persistent terminals and the Amp runner |
| Tailscale | Provide private connectivity and enforce which devices can reach which endpoints |
| 1Password | Hold SSH identities, recovery credentials and individual project secrets |
| Rex | Provide persistent terminal sessions that clients can reconnect to |
| Rootless Docker | Run project containers without a root-owned development daemon |
| Amp | Execute development and deployment tasks on the VPS |
| Cloudflare | Remain available for a future, separately designed public-sharing workflow |

Rex's Linux server and its Mac client are separate components. A remote terminal is only useful while the laptop is closed if the shell and its work are running on the remote machine. Rex supports a Linux server with private Tailscale access; the client connects to that server's address. [Rex remote-access documentation](https://www.superlogical.com/rex/docs/linux/remote-access)

## Two Tailscale devices can represent one VPS

This detail initially looked like duplication. It is a consequence of using two different integrations.

The operating system runs Tailscale for SSH and application previews. Rex also has a built-in Tailscale integration, which joins the network as a separate device. In the examples, those devices are called `workbench` and `workbench-rex`.

They have different responsibilities:

- `workbench` handles SSH and private application HTTPS.
- `workbench-rex` handles Rex control connections.

The addresses should be recorded separately. A preview URL is not automatically the Rex endpoint, and a successful SSH connection does not prove that the Rex client is authorised.

## Keep administration separate

I used an administrator account and an ordinary development account. Here they are called `operator` and `builder`.

The administrator can maintain the operating system with password-protected sudo. The development account owns projects, rootless Docker, the personal Rex service and the Amp runner. It has no general sudo permission.

One small exception lets development work publish a private preview. A root-owned helper accepts a tightly restricted set of ports and a fixed loopback target. It gives the development account a specific operation rather than access to arbitrary Tailscale commands.

That distinction matters once Amp is involved. The host runner executes as `builder`, so it can read that account's project files and control its Docker daemon. A separate container job can receive a smaller set of files and no daemon socket. I need both options, and I need their permissions described accurately.

## Private previews simplify the first version

A preview only needs to reach my devices. The application listens on `127.0.0.1`, and Tailscale Serve provides private HTTPS in front of it. Serve and Funnel have different audiences: Serve is for the tailnet, while Funnel is for public access. [Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve)

Cloudflare therefore has no active role in the initial preview path. I do not need a public DNS record, a domain move or a public tunnel for each experiment. If I later want to share a preview outside my devices, that will need its own access rules and lifetime.

The Amp control connection is another separate path. The runner connects outbound to Amp, which means I do not need to open a public incoming port for it. This still relies on Amp's service and my Amp account. Running the tools on my VPS does not make the entire agent system self-hosted.

## Decide what will count as working

Before installing the application tools, I wrote down the useful outcomes:

1. A fresh private SSH login works with the intended key.
2. The administrator can use sudo, and the development user cannot run arbitrary privileged commands.
3. Rex opens the VPS workspace from the Mac and phone.
4. A container keeps running when the client disconnects.
5. A private preview loads from a second device with normal certificate verification.
6. An Amp task deploys a real application, rather than merely producing deployment instructions.
7. Provider-console recovery works after root SSH has been disabled.

Those checks determine the order of the rest of the series. Private access comes first. Containers and terminals come next. Agent deployment comes after there is a controlled way to run an application and expose its preview.
