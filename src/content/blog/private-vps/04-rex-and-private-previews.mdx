# Rex, private previews and an iPhone connection

*Part 4 of 7. [Previous: rootless Docker](03-rootless-docker.mdx) · [Series index](README.mdx) · [Next: project secrets](05-secrets-with-1password.mdx)*

With private SSH and rootless Docker working, I added the interfaces I would actually use: a persistent Rex workspace and an HTTPS preview that opens on another device.

These are two different services. The Rex endpoint controls terminals. The preview endpoint reaches an application. Keeping their addresses and permissions separate made the phone setup much easier to understand.

## Install the intended Rex package

Follow the vendor's [Linux installation instructions](https://www.superlogical.com/rex/docs/linux/installation), including any current access requirements. Linux support was still in testing when I prepared this setup.

On Ubuntu, inspect the package origin and the installed command:

~~~sh
apt-cache policy rex
rex -v
command -v rex
~~~

Ubuntu also has an unrelated Perl automation package called `rex`. A successful package installation is not enough to identify the product. I used the vendor repository and selected a build compatible with the Mac client. The private provisioning pinned that build deliberately and held it until a planned client/server update.

If you pin an older package, inspect the repository's existing preferences. An equal-priority rule may still leave the newer build selected. Do not copy an obsolete version number from a blog post; choose an available version and verify it on your own clients.

## Run a personal server as the development user

I used a personal Rex service under `builder`, rather than a root login server. Check that unused package-level shared or login-server units are not active alongside it.

As `builder`, create `~/.config/systemd/user/rex.service`:

~~~ini
[Unit]
Description=Personal development Rex server

[Service]
Type=simple
ExecStart=/usr/bin/rex server run --tailscale --tailscale-hostname workbench-rex --tailscale-advertise-tag tag:workbench-rex --tailscale-allow-tailnet-members --log-format text
Restart=on-failure
RestartSec=5
UMask=0077
TimeoutStopSec=30

[Install]
WantedBy=default.target
~~~

The binary path assumes the vendor's Ubuntu package. Adjust it if you deliberately installed the standalone binary elsewhere.

~~~sh
systemctl --user daemon-reload
systemctl --user enable --now rex
journalctl --user -u rex -n 30 --no-pager
~~~

Complete the displayed Tailscale sign-in, approve the named node and verify its tag. Enable tailnet HTTPS certificates and MagicDNS for this integration.

The membership flag is appropriate here only with the restrictive network policy already in place. A tagged node has no personal owner, and Rex admits the tailnet callers that the policy permits. A connection can exercise the server account's authority. This is why I did not put an anonymous listener on a public address. [Rex's listener and authorisation documentation](https://www.superlogical.com/rex/docs/linux/remote-access)

In the Mac app, add `https://workbench-rex.YOUR_TAILNET.ts.net:443` as a remote host. Create a workspace there, then verify `whoami`, `hostname` and the project directory in its terminal.

CLI host entries and GUI entries did not synchronise in the build I used. If the CLI works and the app does not, inspect both configurations rather than assuming they share a saved host list.

## Start a small application on loopback

As `builder`, create `~/projects/demo`. Put a non-sensitive test marker in `index.html`, then add this Dockerfile:

~~~dockerfile
FROM python:3.12-slim
WORKDIR /site
COPY --chmod=0644 index.html /site/index.html
USER 65534:65534
CMD ["python", "-m", "http.server", "8080", "--bind", "0.0.0.0", "--directory", "/site"]
~~~

The explicit file mode matters because the host services use a restrictive umask. The application user must be able to read the copied static file.

Add `compose.yaml`:

~~~yaml
services:
  web:
    build: .
    ports:
      - "127.0.0.1:3000:8080"
    restart: unless-stopped
    cpus: 0.25
    mem_limit: 128m
    pids_limit: 64
    cap_drop: [ALL]
    security_opt:
      - no-new-privileges:true
~~~

The HTTP server listens on the container's interfaces. Docker publishes it only on the host's loopback address. Start it and check that binding:

~~~sh
docker compose up -d --build
docker compose ps
curl --fail http://127.0.0.1:3000/
ss -lnt 'sport = :3000'
~~~

The local check should succeed before HTTPS is added.

## Put private HTTPS in front

An administrator can configure the route directly:

~~~sh
sudo tailscale serve --bg --https=8443 http://127.0.0.1:3000
sudo tailscale serve status
~~~

The preview is `https://workbench.YOUR_TAILNET.ts.net:8443/`. Serve handles the private HTTPS connection and forwards to the local application. With background mode, the configuration persists beyond the terminal session. [Tailscale's Docker preview example](https://tailscale.com/docs/solutions/host-private-server-docker)

I used a separate HTTPS port for each project. The example allocation is local ports 3000 to 3999 and HTTPS ports 8443 to 8499. This avoids teaching every framework to run under a shared URL prefix.

Use normal certificate verification from the Mac. Do not use `curl -k` to turn a certificate failure into a passing test.

## Allow preview changes without general sudo

Amp will need to publish previews as `builder`. I gave it a narrowly scoped helper rather than general Tailscale administration.

Save this adapted example as `workbench-preview` and inspect it before installation:

~~~python
#!/usr/bin/python3 -I
import subprocess
import sys


def port(value, first, last):
    if not value.isascii() or not value.isdigit():
        raise SystemExit("expected an integer port")
    number = int(value)
    if not first <= number <= last:
        raise SystemExit("port outside the preview range")
    return number


def main():
    args = sys.argv[1:]
    if args == ["status"]:
        return subprocess.call(["/usr/bin/tailscale", "serve", "status", "--json"])
    if len(args) not in (2, 3) or args[0] not in ("set", "remove"):
        raise SystemExit("usage: set HTTPS_PORT LOCAL_PORT | remove HTTPS_PORT | status")
    https = port(args[1], 8443, 8499)
    command = ["/usr/bin/tailscale", "serve", "--bg", f"--https={https}"]
    if args[0] == "set" and len(args) == 3:
        local = port(args[2], 3000, 3999)
        command.append(f"http://127.0.0.1:{local}")
    elif args[0] == "remove" and len(args) == 2:
        command.append("off")
    else:
        raise SystemExit("invalid arguments")
    return subprocess.call(command)


if __name__ == "__main__":
    raise SystemExit(main())
~~~

As administrator, install it as root-owned mode `0755` at `/usr/local/sbin/workbench-preview`. Verify that the parent directory is also administrator-owned. Use `visudo` to create `/etc/sudoers.d/workbench-preview`, mode `0440`, with:

~~~sudoers
builder ALL=(root) NOPASSWD: /usr/local/sbin/workbench-preview *
~~~

Validate the sudoers file with `visudo -cf /etc/sudoers.d/workbench-preview`. Then test the interface as `builder`:

~~~sh
sudo -n /usr/local/sbin/workbench-preview set 8443 3000
sudo -n /usr/local/sbin/workbench-preview status
sudo -n -l
~~~

The wildcard in sudoers is safe only in combination with a helper that rejects unsupported arguments before starting a privileged process. This helper constructs argument lists without a shell, accepts only numeric ports in fixed ranges and always targets `127.0.0.1`. Python's isolated mode avoids user-controlled Python import settings.

The development user can replace previews within the reserved range. It cannot choose arbitrary remote targets or use this helper to configure Funnel. The helper is a privileged programme, so review any future changes as such. The command shapes follow the [Serve CLI reference](https://tailscale.com/docs/reference/tailscale-cli/serve).

## Add the iPhone as a separate client

First connect the phone to the same Tailscale network. To allow Rex, add the verified `PHONE_TS_IP` to the Rex grant from part 2:

~~~json
{
  "src": ["MAC_TS_IP", "MAC_REX_TS_IP", "PHONE_TS_IP"],
  "dst": ["tag:workbench-rex"],
  "ip": ["tcp:443"]
}
~~~

Update its policy test to match:

~~~json
{
  "src": "PHONE_TS_IP",
  "accept": ["tag:workbench:8443", "tag:workbench-rex:443"],
  "deny": ["tag:workbench:22", "tag:workbench:5432"]
}
~~~

Review and save that specific access expansion. Direct phone SSH remains outside the grant.

In Rex iOS, add the VPS address, `https://workbench-rex.YOUR_TAILNET.ts.net:443`, and open the server's workspace. If the Mac is already paired, keep that entry. It represents a different server.

The Mac's pairing QR code in this build advertised the Mac's own Rex server, even while a VPS connection existed. Checking the address avoided pairing the wrong host again. I entered the VPS address separately on the phone.

Finally, inspect `rex client ls` on the VPS. I checked the native iPhone client's presence and authenticated principal as well as the Mac's connection. A successful preview in Safari had proved browser access; this separate check proved Rex control access.
