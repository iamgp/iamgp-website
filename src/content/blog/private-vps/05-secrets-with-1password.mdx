# Giving a job one secret

*Part 5 of 7. [Previous: Rex and previews](04-rex-and-private-previews.mdx) · [Series index](README.mdx) · [Next: the Amp runner](06-amp-runner-and-deployments.mdx)*

The SSH private key stayed in 1Password on my Mac. I wanted a similar separation for application credentials: a job should receive the value it needs without gaining access to my password manager.

For this setup, the Mac retrieves selected fields and sends them over the verified SSH connection. The VPS does not receive a personal 1Password session or a credential that can read the whole development vault.

## Separate the kinds of credentials

I kept distinct roles for the provider's root recovery credential, the administrator's sudo password, the SSH identity, Amp's own sign-in and each project's application credentials.

A database password should belong to the relevant application and environment. It should not be an infrastructure recovery password reused under a different variable name. A private-repository credential should likewise be restricted to the repository and operations it needs.

The 1Password CLI retrieves the selected vault fields on the Mac, with the desktop app unlocked and its normal authorisation in place. The VPS receives only the values needed for the job.

## Keep references in configuration

A reference identifies a field without containing its value. An example for a fictional vault and item is:

~~~text
op://Engineering/Transport check/value
~~~

The CLI can resolve that reference with `op read`. Its `--no-newline` option avoids adding a newline to the retrieved value. [1Password's read command](https://www.1password.dev/cli/reference/commands/read)

A reference can still reveal private project names or account structure. I treat it as configuration metadata rather than something to print casually in a public article. The names in this series are invented.

For the transport check below, create a disposable test item whose field contains the non-sensitive marker `transport-check-only`. Test the route with that marker before using it for a real application's credential.

## Send the value through stdin

There are several ways to accidentally expose a secret: interpolate it into an SSH command, put it in a Docker argument, enable shell tracing, or write it to a temporary file that survives the task.

The launcher used structured data over SSH stdin. The command line named a fixed receiver. It did not contain a secret value. The receiver validated the request before starting the container.

The example below runs a fixed transport check with one value, `DEMO_TOKEN`. It does not accept a command or an image name from the request.

As `builder` on the VPS, save the following at `/home/builder/.local/bin/receive-demo-job`, owned by `builder` with mode `0700`. Create that directory first if needed.

~~~python
#!/usr/bin/python3 -I
import json
import os
import subprocess
import sys

raw = sys.stdin.buffer.read(65537)
if len(raw) > 65536:
    raise SystemExit("request too large")
payload = json.loads(raw)
if not isinstance(payload, dict) or set(payload) != {"DEMO_TOKEN"}:
    raise SystemExit("unsupported request")
value = payload["DEMO_TOKEN"]
if not isinstance(value, str) or not value or "\u0000" in value:
    raise SystemExit("invalid named value")

environment = os.environ.copy()
environment["DEMO_TOKEN"] = value
command = [
    "/usr/bin/docker", "--context", "rootless", "run", "--rm", "--init",
    "--cap-drop=ALL", "--security-opt=no-new-privileges",
    "--cpus=0.25", "--memory=128m", "--pids-limit=64",
    "--env", "DEMO_TOKEN", "python:3.12-slim", "python", "-c",
    "import os; assert os.environ['DEMO_TOKEN'] == 'transport-check-only'; print('transport check passed')",
]
subprocess.run(command, env=environment, check=True)
~~~

The NUL-character check above is written as the Python escape `\u0000`; it rejects values that cannot be used as environment strings.

On the Mac, install and authenticate the 1Password CLI using its supported desktop integration or sign-in flow. Save this sender as a local Python file and run it with `python3`:

~~~python
import json
import subprocess

reference = "op://Engineering/Transport check/value"
result = subprocess.run(
    ["op", "read", reference, "--no-newline"],
    capture_output=True,
    text=True,
)
if result.returncode:
    raise SystemExit("1Password could not supply the test value; no job started")

request = json.dumps({"DEMO_TOKEN": result.stdout}).encode()
subprocess.run(
    [
        "ssh", "-T", "-o", "ForwardAgent=no",
        "-o", "StrictHostKeyChecking=yes", "workbench",
        "/home/builder/.local/bin/receive-demo-job",
    ],
    input=request,
    check=True,
)
~~~

The output should say that the transport check passed. It should not print the value. This is an example for a known non-secret marker, not an application-secret receiver to deploy unchanged everywhere.

The actual setup's more general helper also validated project names, project-directory containment, image arguments, argument lists and allowed environment names. I tested the transport with a non-secret vault field before treating it as a route for later project onboarding.

## Environment names need validation too

A variable name can change what the launcher does. Accepting arbitrary input such as `DOCKER_HOST`, `DOCKER_CONTEXT`, `PATH` or `PYTHONPATH` would let a request affect the execution environment rather than just the application.

The small example avoids that problem by accepting exactly `DEMO_TOKEN`. A general launcher needs an explicit policy for names, not merely a check that they look like uppercase words. The launcher reserved control variables and prefixes used by Docker, Python, the loader and the session environment.

The same care applies to project paths. A name should not escape the projects directory through `..`, a symlink or an unexpected mount. A command should be passed as an argument list, with a clear separation between launcher options and the command being run.

## Stdin does not make a value invisible

This transport avoids putting the value into SSH arguments or a helper-created file. The value still exists in process memory. When an application receives it as an environment variable, Docker's container configuration can contain it too.

Anyone who controls the development Docker daemon may be able to inspect those values. The host Amp runner will have that authority because it runs as the same development account. A constrained job receives no daemon socket, but that does not isolate its credential from the daemon's owner or host administrators.

An application can also log its own credentials. Output filtering and a careful launcher cannot compensate for code that prints a connection string.

For an application that needs a file-based secret or another delivery method, design that workflow for the application. 1Password documents several [script-injection approaches](https://developer.1password.com/docs/cli/secrets-scripts); none removes the need to decide which process is authorised to receive the value.

The Mac remains responsible for reading the vault. The VPS job receives only the selected values.
